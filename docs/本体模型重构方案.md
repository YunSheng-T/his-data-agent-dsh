# 本体模型重构方案（数据开发 · V2）

> 目标：把「本体驱动扫描」的本体定义层从 V1（provider-mock.js 的 JobType/Policy/Rule/RuleImpl 简版）重构为贴合真实数据开发的本体模型。
> 关键输入：数据开发分四类平台，平台下有多个平台实例（数据ETL → FlashSync/BDS，低代码 vs 高代码）；每个平台实例有自己的作业类型（FlashSync → 传输任务/加工任务）；作业类型下面目录→作业。
> 关键结论：Policy（治理目标）跨平台，Rule 挂平台，RuleImpl 挂作业类型。

## 一、新本体模型（四层）

    数据开发
    └ 平台分类（四类：数据库脚本 / 数据ETL / 数据调度 / 数据服务）
        └ 平台实例（FlashSync / BDS / Dolphin…）     ← 低代码/高代码、格式/解析器/规则不同
            └ 作业类型（传输任务 / 加工任务 / 数据库脚本…）  ← 属于具体平台实例
                └ 目录 → 作业                          ← 作业树（叶子=具体作业）

Definition 层四个概念（职责分层）：

| 概念 | 挂载点 | 作用 |
|---|---|---|
| Policy（治理目标） | 跨平台 | 为什么查——大颗粒，聚合多条 Rule，横跨 SQL/ETL（如 设计开发一致性） |
| 平台（分类/实例） | JobType 层级 | 哪个域——Rule 的语义归属；RuleImpl/解析器绑定到平台实例 |
| Rule | 平台 | 查什么——具体规则（如 字段类型一致性），属某个 Policy，挂某个平台 |
| RuleImpl | 作业类型 | 怎么查——Rule 在特定作业类型上的实现（一 Rule 多实现） |

## 三、扫描计划装配逻辑

    作业 →(manifest.yaml 目录→平台实例 + 文件头 @platform: + AST/内容)
      → 定位 平台实例 → 作业类型
      → 取该平台的所有 RULE（RULES 里 platform=平台）
      → 每条 RULE 查 RULE_IMPL（rule × jobType → 实现）
      → 按 POLICY 分组（归因链：R-102 ← 字段类型一致性 ← 设计开发一致性 ← 数据ETL·加工任务 ← 平台+内容信号）

## 四、旧模型（V1）GAP 分析

### 可直接归纳的旧要素（无需推倒）

| 旧要素 | 归纳到新模型 |
|---|---|
| POLICIES（consistency/script-quality/sql-safety…） | 新 Policy（跨平台治理目标）——去掉 jobType 绑定（appliesTo 职责交给平台+RuleImpl） |
| RULES（R-101/R-102/R-103/R-301…） | 新 Rule（补 platform + policy 归属） |
| RULE_IMPL（se-sql 1.8） | 新 RuleImpl（拆成按作业类型多实现） |
| JOB_TYPES 的平台族概念（dbscript-platform） | 新：平台分类（第一级） |
| FINDINGS / RESOLUTION_TRACE | 实例层，保留 |
| DESIGN_INCREMENT / CODE_INCREMENT | 引用层对账事实，保留 |

### GAP（旧设计缺 / 错，需修正）

| # | GAP | 说明 | 新设计处理 |
|---|---|---|---|
| 1 | 缺「平台实例」层 | 旧只有 dbscript-platform 单实例，无法表达 FlashSync/BDS/Dolphin 多实例 | 平台分类→平台实例→作业类型 三级 |
| 2 | Policy 绑 jobType（appliesTo） | 与「Policy 跨平台治理目标」矛盾（设计开发一致性 SQL/ETL 都有） | Policy 去 appliesTo，跨平台聚合 |
| 3 | Rule 与 RuleImpl 未分离 | 旧一 Rule 一 impl，stage/severity 全局 | Rule 挂平台；RuleImpl 拆出按作业类型（一 Rule 多实现） |
| 4 | RuleImpl 单一（se-sql 1.8） | 不区分平台实例/作业类型（低代码 vs 高代码解析不同） | RuleImpl 绑「平台实例 × 作业类型」 |
| 5 | 引用层硬编码投影（MODELS/RELEASES） | 与「零绑定、零存储」冲突（implements/releaseBaseline 应现场取） | 引用层投影只存标识+关系，锚点现场匹配/取值 |
| 6 | 路由 PACKAGE_REGISTRY 前缀硬编码 | 目录名不随用户习惯（可能 etl/bds 或直接 bds） | 改 manifest.yaml 驱动「目录→平台实例」 |
| 7 | 缺「作业树（目录→作业）」表达 | 实例层只有 JobType 类型，无目录/作业投影 | 作业类型之下是「目录→作业」投影 |

## 五、落地步骤（建议顺序）

1. 平台/实例/路由：provider-git/provider-tenants 改读 manifest.yaml（目录→平台实例）；JOB_TYPES 重构成「平台分类→平台实例→作业类型」
2. Rule/RuleImpl 分离：RULES 挂平台 + RULE_IMPLS 按作业类型（provider-mock 拆成两表）
3. Policy 跨平台：POLICIES 去 appliesTo，跨平台聚合（归因链走它）
4. 扫描计划装配：scanScriptJob/scanEtlJob 改为 作业→平台实例→作业类型→Rule→RuleImpl→Policy 分组
5. 引用层现场化：implements 物理表名现场匹配、releaseBaseline 现场取 DevOps
6. 回归：assert-ontology 更新（新结构断言）+ 全量回归
