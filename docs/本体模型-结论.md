# 数据开发本体 · 设计结论（定稿 · 2026-08）

> 本结论是「本体驱动扫描」下一轮迭代的基准。由讨论会沉淀：平台两层、Rule/RuleImpl 分离、Policy 跨平台、SQL 特殊域、manifest 驱动。
> 配套文件：docs/本体模型.owl（OWL 2 Turtle）、docs/本体模型-实体属性关系.xlsx（平台手工创建）、docs/本体模型-实体属性关系清单.md（阅读版）、docs/本体模型重构方案.md（旧→新 GAP 与落地步骤）。

## 一、达成的设计决策（不可推翻）

1. 平台两层，两个实体都保留：
   - PlatformType（平台类型）：四类取值 dbscript(数据库脚本) / etl(数据ETL) / sched(数据调度) / svc(数据服务)。
   - PlatformInstance（平台实例）：具体平台（ETL → FlashSync/BDS；调度 → Dolphin）。低代码/高代码，格式/解析器/规则不同。
2. 四类平台不建子类（不用继承）：PlatformType 是一个实体，四类是它的取值（枚举），不是 DataScriptPlatform 等四个类。
3. JobType 层级：PlatformType →(hasPlatformInstance)→ PlatformInstance →(hasJobType)→ JobType →(instanceOf)→ Job →(inDirectory)→ Directory。
4. Policy（治理目标）跨平台、大颗粒：如「设计开发一致性」横跨 SQL/ETL；Policy →covers→ PlatformType（可覆盖多个平台类型）。
5. Rule 挂平台类型：Rule →hasPlatform→ PlatformType（字段类型一致性挂 etl）。
6. RuleImpl 挂作业类型：RuleImpl →bindsJobType→ JobType；一 Rule 多实现（同一条 Rule 在 传输任务/加工任务 上实现不同，低代码 vs 高代码）。
7. SQL 是特殊域：L1 数据库模型 → L2 生成平台(DataDesign/UDP) → L3 数据库脚本(.sql)；不论哪个平台生成，底层都是 .sql，故「数据库脚本」作业类型的 RuleImpl 统一。
8. 路由由 manifest.yaml 驱动：代码仓目录名不固定（可能 etl/bds 或直接 bds），目录→平台实例映射由 manifest.yaml 声明，不能按目录名前缀硬编码。
9. 零绑定、零存储：implements 靠物理表名现场匹配推导；releaseBaseline 靠 DevOps 最近发布现场取值；本体只存投影标识+关系，不复制大对象、不落元数据到仓。

## 二、最终本体模型

    数据开发
     └ PlatformType（平台类型 · dbscript / etl / sched / svc）
         └ hasPlatformInstance
             └ PlatformInstance（平台实例 · FlashSync / BDS / Dolphin）
                 └ hasJobType
                     └ JobType（作业类型 · 传输任务 / 加工任务 / 数据库脚本）
                         └ instanceOf → Job → inDirectory → Directory

    Policy（治理目标 · 跨平台）──covers──▶ PlatformType
      │ containsRule
      ▼
    Rule（规则）──hasPlatform──▶ PlatformType
      │ hasRuleImpl
      ▼
    RuleImpl（规则实现）──bindsJobType──▶ JobType

    引用层：Model · ModelVersion · ModelIncrement · CodeIncrement · Release
    实例层：ScanRun · Finding · ResolutionTrace

## 三、定义层关系总表

| 关系 | 来源 → 目标 | 基数 | 说明 |
|---|---|---|---|
| hasPlatformInstance / platformOf | PlatformType → PlatformInstance | 1:N | 平台类型含实例 |
| hasJobType / definedBy | PlatformInstance → JobType | 1:N | 实例有作业类型 |
| instanceOf | Job → JobType | N:1 | 作业分类 |
| inDirectory | Job → Directory | N:1 | 作业树 |
| covers | Policy → PlatformType | M:N | 策略覆盖平台（跨平台） |
| containsRule | Policy → Rule | 1:N | 聚合规则 |
| hasPlatform | Rule → PlatformType | N:1 | 规则挂平台 |
| hasRuleImpl | Rule → RuleImpl | 1:N | 一规则多实现 |
| bindsJobType | RuleImpl → JobType | N:1 | 实现挂作业类型 |
| implements / hasVersion / hasIncrement / matchesIncrement | 作业↔模型 等 | | 引用层（四态 MATCH/AHEAD/BEHIND/DIVERGE） |
| releaseBaseline | Release → Job | 1:N | 最近发布即基线 |
| generatedBy / violates / traceOf | 实例层溯源 | | 回挂本体 |

## 四、现有实现（feature/ontology-scan-v15）相对本结论的待调整点

当前 @his/domain-tools-ontology（provider-mock.js）已实现 P1-P4 本体扫描（JobType 平台族→形态→叶子、Policy 绑 jobType、Rule 带 impl、单引擎 se-sql），与结论的差异：

| 现状 | 按结论调整 |
|---|---|
| JOB_TYPES 两级（平台族→形态→叶子） | 重构为 平台类型 → 平台实例 → 作业类型 三级 |
| 无 PlatformInstance（FlashSync/BDS 未建模） | 加 PlatformInstance（style 低代码/高代码、defaultEngine） |
| POLICIES 绑 jobType（appliesTo） | Policy 跨平台，改 covers PlatformType |
| RULES 带单一 impl/stage/severity | Rule 挂平台类型；RuleImpl 拆出按作业类型多实现 |
| 单引擎 se-sql 1.8 | 按平台实例/作业类型多引擎（flashsync-parser / bds-parser） |
| PACKAGE_REGISTRY 前缀硬编码 | 改读 manifest.yaml（目录→平台实例） |
| 演示作业仅 dbscript | 可加 etl/flashsync、bds 多实例演示 |

落地顺序建议：① manifest 路由 + 平台两层（provider-*）→ ② Rule/RuleImpl 分离（provider-mock 两表）→ ③ Policy 跨平台 → ④ scanScriptJob 装配（作业→实例→类型→Rule→RuleImpl→Policy 分组）→ ⑤ 引用层现场化 → ⑥ 回归（assert-ontology 更新 + 全量）。
