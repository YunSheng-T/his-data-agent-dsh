# 多租户部署方案（两层隔离模型）

> 状态：方案沉淀 · 不实施。本文档把多租户改造的方向与架构定型，供后续改造前评审。
> 核心结论：租户隔离是两层，缺一不可——第一层「租户间」进程隔离，第二层「租户内」会话级状态隔离。

## 1. 背景与约束

HIS Data Agent 跑在 DeepSeek Harness（DSH）之上。DSH 是一个单进程 Cordis 应用，且会话有状态，绑定了进程内资源：

| 状态 | 现状位置 | 并发后果 |
|---|---|---|
| 当前租户 this.current | provider-tenants.js 的 TenantRepoProvider.current | 进程级单例，switchTenant() 改全局，多会话互串 |
| 锚定 current | workspace-anchor/index.js 模块级变量 | 全局单例，多会话互相覆盖 |
| git working tree / HEAD | 每租户仓本地目录 | checkout/写工作区是仓级全局，并发冲突 |
| Provider 实例（sched/dryrun/cicd） | apply() 里 new 一次 | 进程级共享 |

结论：DSH 不能像无状态 API 那样直接水平扩展，隔离必须显式建模。

## 2. 两层隔离模型

第一层（租户间）：进程 / namespace 隔离 —— 隔离边界 = 进程边界 + 数据目录边界。
第二层（租户内）：会话级状态隔离 —— 租户 = 数据团队，团队内多用户/会话并发。

### 2.1 第一层：租户间进程隔离

一个租户 = 一个独立 DSH 实例（进程 / Pod）。租户边界即进程边界，一次解决：租户间 checkout 不互相干扰、锚定/当前租户单例不串、崩溃只影响单租户。DSH 本体零改动，外面只加「网关 + 编排 + 存储」。

### 2.2 第二层：租户内会话级状态隔离

租户 = 数据团队，一个租户实例内部仍有多用户/会话并发，三处状态需 per-session 化：

| 状态 | 方案 |
|---|---|
| 锚定 | per-session：Map<sessionId, anchor> 或 AsyncLocalStorage |
| checkout / HEAD | 「锁 + readCommitted」打底（读走 committed 不碰 working tree）；后续可升级 git worktree 或对象级读写 |
| 写工作区 | per-租户写锁（先）；对象级读写（路线 B 前段，后置） |

## 3. 业界对标

### 3.1 ChatGPT / DeepSeek 三层隔离

| 层 | 隔离手段 | 关键技术 |
|---|---|---|
| 推理层（共享 GPU 池） | 软隔离：配额 + 熔断 + 限流 | cgroup（CPU weight / memory limit）、LoRA per-tenant、KV cache 隔离、X-Tenant-ID + HMAC 路由 |
| 会话/应用层 | 无状态，租户上下文靠 token/header 传递 | 会话历史存 Redis/DB，网关无状态水平扩、密钥轮换/设备绑定/异常检测 |
| 数据层 | 硬隔离 | 行级 / 独立库 / 独立 schema + 加密审计 |

关键差异：ChatGPT 会话 = 无状态消息序列（落 DB），可无状态池化；DSH 会话 = 有状态（git 仓 + working tree + 锚定），必须进程级隔离。

### 3.2 DSH 社区现成方案

| 方案 | 模型 | 隔离边界 |
|---|---|---|
| dsh-hub | JupyterHub 风格 | PAM 登录，每用户一个独立 dsh 进程（独立 uid/gid + 数据目录 + iptables 端口防护），cookie 路由 HTTP/WS，带 idle culling |
| dsh-isolated-runtime | K8s-native | 一个租户 = 一个 namespace = 一个 Cell（Pod），Envoy Gateway + OIDC + RBAC，CSI 快照/恢复，镜像 digest 固定 |

参考链接：
- dsh-hub: https://github.com/Mpaperlee/dsh-hub
- dsh-isolated-runtime: https://github.com/GuoMonth/dsh-isolated-runtime

两者殊途同归：per-user / per-tenant 独立实例，不搞进程内多租户。

## 4. 架构总览（四层）

网关（唯一入口）：租户解析 · 鉴权 · 配额/熔断 · 会话粘性路由
  → tenant→实例 路由表
编排：spawner(冷启动) · idle culler(回收) · 快照
  → 实例 T1..Tn：每租户一个 DSH 进程，独立 DSH_HOME/数据目录/端口，uid/gid 或 namespace 隔离
存储：每租户数据目录(git仓+会话+模型) + 租户元数据(映射/配额/权限) + 快照(回收前落盘/恢复)

| 组件 | 职责 | 对标 |
|---|---|---|
| 网关 | 租户解析（OIDC token/域名）、鉴权（OIDC + RBAC）、会话粘性（cookie 绑定 tenant→实例）、配额/熔断 | Envoy Gateway / DeepSeek 推理网关 |
| 编排 | spawner 首次访问拉起实例、idle culler 空闲回收、快照/恢复 | JupyterHub spawner + idle-culler |
| 实例 Cell | 每租户一个 DSH 进程，独立 DSH_HOME + 数据目录 + 端口，uid/gid 或 namespace 隔离，launcher 托管子进程 | dsh-hub / dsh-isolated-runtime |
| 存储 | 每租户数据目录 + 租户元数据外置 + 快照 | CSI snapshot |

## 5. 请求生命周期

1. 用户 OIDC 登录 → 网关拿到 tenantId
2. 查路由表：有实例 → 粘性路由；无 → spawn
3. spawn：launcher 起 DSH 进程，注入 HIS_TENANT_ID 环境变量
4. DSH 启动，HIS 插件读 HIS_TENANT_ID 只 mount 该租户仓
5. 会话内锚定/checkout 按 session 隔离（第二层）
6. 会话结束 → 空闲计时超时 → 回收 → 快照落盘

## 6. 容量模型（1000 租户）

- 同时在线假设 1–5% → 10–50 个热实例常驻，其余冷启动（profile 加载 ~秒级）
- 空闲回收默认 30 分钟
- 存储：每租户 git 仓 + 模型假设几百 MB → 1000 租户 ~几百 GB，对象存储 + 快照分层

## 8. 部署形态两档

- 单机内网：dsh-hub 模式（PAM + per-user 进程 + cookie 路由），适合几十租户。
- K8s 生产：dsh-isolated-runtime 模式（namespace = 租户 + Cell + OIDC/RBAC + CSI），适合 1000 租户。
