# Data Agent 业界对标 · 洞察

> 目的：理解业界「数据 Agent」产品（Genie/Databricks、DataBuddy/腾讯、瑶池/阿里）的架构、业务场景与价值，对齐 HIS Data Agent 的定位。
> 信息源：官方文档（Databricks Genie Agents concepts）+ 公开产品信息 + 领域知识。生成日期 2026-08。

## 一、产品图谱

| 产品 | 厂商 | 一句话定位 |
|---|---|---|
| **Genie (Data Agents)** | Databricks | Lakehouse 上的语义层 + 自然语言问数（业务用户），含只读/Inspect/代理模式 |
| **Cortex Agents / Analyst** | Snowflake | 数据云内建 text-to-SQL + 数据 Agent |
| **Amazon Q (data agent)** | AWS | Q 生态的 data agent 能力，连多数据源做查询/分析 |
| **DataBuddy** | 腾讯云 | 数据开发/数据工程 **Coding Agent**（生成 ETL/SQL、数据建模），嵌入数据平台 |
| **WeData + AI 原生底座** | 腾讯云 | DataBuddy 的宿主：数据平台面向 Agent 升级 |
| **瑶池 Data Agent** | 阿里云 | **全生命周期**数据智能体（开发+治理+运维），DataWorks 生态 |
| **开悟 Data Agent** | 开普云 | 数据智能体平台 |

## 二、三家深度剖析

### Genie（Databricks）· 语义层 + Data Agent 架构
- **复合 AI 系统**（非单一 LLM）：组合多个交互组件处理任务。
- **语义层 = 五个策展组件**（agent 级，不改底层元数据）：
  - 知识存储（表/列说明、同义词、联接关系、SQL 表达式、提示匹配）
  - 说明 Instructions（业务规则、术语、日期格式、领域上下文）
  - 示例 SQL 查询库（智能挑选）
  - SQL 函数（作者已验证逻辑）
  - 基准测试（评估准确性）
- **数据基础**：只基于 Unity Catalog 注册数据（托管表/视图/指标视图/物化视图），用目录元数据（PK/FK、表列说明）+ 语义层生成 SQL。
- **关键机制**：生成查询**始终只读**；**Inspect**（高级推理审查/改进 SQL）；**代理模式**（多步推理、跑多个 SQL、迭代产出综合报告）；**Genie Code Agent 模式**（自动处理代码/流水线/仪表板）。
- **限制**：聊天模式只处理结构化数据；复杂查询用 Inspect 提置信度。

### DataBuddy（腾讯）· Coding Agent
- **定位**：数据开发/数据工程 Coding Agent（HIS 直接参照它）。
- **核心哲学**（"从人操作工具到 Agent 替人干活"）：
  1. **Agent 替人干活**（自然语言下指令，Agent 完成开发动作）
  2. **深度理解数据/元数据/数据地图**（像 Coding Agent 理解代码仓库）
  3. **代码生成 + 校验 + 调试**（落地到真实平台）
- **机制**：模型（混元/DeepSeek）+ 腾讯数据平台（WeData）+ 元数据/数据地图；自然语言 → 生成 .sql/.etl、数据建模、数据开发；人机协同（生成→确认→执行）。
- **与 HIS**：HIS 走的就是这条路线——数据开发工作台内置 Coding Agent（生成 .model/.etl/.dag/.ops + 审批门禁）。

### 瑶池 Data Agent（阿里）· 全生命周期
- **定位**：全生命周期数据智能体（DataWorks 生态），一站式开发+治理+运维 Agent。
- **机制**：DataWorks 平台 + LLM（Data+AI 驱动）；数据开发（建表/写 SQL/调优/诊断）→ 数据治理（质量/规范/标准）→ 数据运维（监控/调度/告警）；开发 AI 助手（代码生成/智能调优/异常诊断）。

## 三、共性范式（Data Agent 的"满分答案"）

1. **数据平台内嵌 Agent**（非独立工具）。
2. 核心 = **语义/元数据理解**（让 Agent 懂数据）+ **自然语言→代码/SQL 生成** + **人机边界 + 可溯源**。
3. **语义层/数据地图**是让 Agent "懂业务口径"的地标（Genie 知识存储 / DataBuddy 数据地图 / 瑶池规范）。

## 四、业务场景 · 用户 · 问题 · 价值点

| 产品 | 业务场景 | 主要用户 | 解决什么问题 | 价值点 |
|---|---|---|---|---|
| **Genie** | 业务用户**自然语言问数**（如"一段时间销量最大的产品"），生成 SQL + 可视化做决策 | 业务团队（销售/财务/运营）、分析师 | 业务想要数据但不会/不想写 SQL；数据团队疲于响应临时取数 | 自助问数（降门槛/响应）；语义层保证口径一致（减少错误查询）；只读安全；**Inspect** 保准确；场景/结果**可复用**；**代理模式**做复杂探索分析（从"发生了什么"到"将发生什么"的预测） |
| **DataBuddy** | 数据工程师**开发数据作业**（ETL/SQL/建模），自然语言生成代码 | 数据开发/数据工程师 | 写 SQL/ETL、调表结构耗时；平台操作繁琐 | **Agent 替人干活**（生成代码、自动开发）；**深度理解数据地图**（减理解成本）；代码生成+校验+调试（提质量）；嵌入平台（免切工具） |
| **瑶池** | **全生命周期**数据（开发/治理/运维）一站式 | 数据开发、数据治理、数据分析师（+业务） | 开发/治理/运维分散低效；SQL 调优、异常诊断耗时 | **全栈智能**（Data+AI）：自然语言建表/写 SQL/调优/诊断；AI 助手提升开发/治理/运维效率；赋能决策（"让企业决策像开挂"） |

**共性价值闭环**：三者都围绕"**让数据触手可及、让开发提效、让口径一致、让安全可控**"——只是切入角度不同（Genie 偏问数、DataBuddy 偏开发、瑶池偏全生命周期）。

**对 HIS 的价值拼图**（HIS 已覆盖哪些、缺口在哪）：
- ✅ 已覆盖：数据开发（建模/ETL/调度，DataBuddy 路线）、治理（本体扫描/规则质检、比 Genie 语义层更深）、安全（审批门禁 fail-closed）、可溯源（Session Log/审计）。
- ⬜ 缺口可借鉴：**问数**（自然语言数据查询，Genie/Cortex 核心；HIS 目前偏"生成作业代码"）；**语义层/口径**（Genie 知识存储，把业务口径建模层）；**全生命周期治理/运维**（瑶池；HIS 有 ops 编排，可扩资产治理/质量门）。


## 五、对 HIS Data Agent 的洞察

1. **路线选对了**：HIS = DataBuddy 的"数据开发 Coding Agent"路线 + **本体化治理**（比 Genie 语义层更深：Genie 偏"问数/口径"，HIS 本体偏"规则/合规/质检"，即"扫什么/为什么"由本体推演）。
2. **差异化机会**：业界多为"自然语言问数/生成代码"；HIS 多了 **强审批写链路（fail-closed）+ 代码仓 CICD（像管代码一样管数据作业）+ 本体驱动扫描**——"数据生产安全 + 治理合规"的纵深。
3. **可借鉴**：
   - Genie Inspect（生成后验证 SQL 准确性）→ HIS 的 `etl_codegen/dag_gen` 生成后自检
   - Genie 语义层/知识存储（业务口径建模）→ HIS 本体可往"业务语义层"扩展
   - 瑶池全生命周期 → HIS 从"建模/开发"扩展到"治理/运维"（已有 ops 编排）
