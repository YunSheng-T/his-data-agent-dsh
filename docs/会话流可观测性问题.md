# 会话流可观测性问题记录（待纳入焕新）

> 性质：不是 bug，是「分层取全」设计的正确行为 + 前端扁平渲染导致的可观测性缺失。

## 一、问题现象

本体驱动扫描场景（dbscript/*.sql）：会话流里获取策略正常，获取规则(policy_get_rules)变成多个步骤看着重复，获取规则实现(rule_get_implementations)更多、个数不稳定，一度怀疑是按钮没防抖。

## 二、根因（session log 实证）

一个 step = 一次模型决策回合；step 内多个 tool/call = 那一次决策批量要了多个工具结果。
证据：assistant/message 的 content 数组一次含 3 个 tool-call block(policy_get_rules x3)，后续 tool/call 的 callId 连续(call_00/01/02)、参数各不同(3 个不同 policy)。
调用次数由本体数据决定：dbscript 平台被 3 组策略覆盖 -> policy_get_rules x3；4 条规则 -> rule_get_implementations x4。符合「策略与规则必须分层取全」约定，不是重复。

## 三、可观测性缺口（前端 renderEvents）

1. assistant/message 只提取 text 渲染气泡，忽略 content 里多个 tool-call block，丢失「这一次回复要了哪些工具」语义；
2. 每个 tool/call 独立 foldCard，3 个同名 policy_get_rules 铺成 3 张独立卡；
3. step/start 只加「步骤 N」文字标签，没把「步骤 → 本次回复的多个工具」组织成整体。
结果：同名工具卡平铺，用户看不出「一次回复批量要 3 个不同策略」，误判重复/卡住。

## 四、方向：回合分组（对齐 DSH-Desktop）

把扁平事件流改为「按 assistant 回合分组」：一次模型回复(reasoning+text+N 个 tool-call+各自 result)作为一个整体单元，工具调用挂在该回合下。
- assistant/message 收到时若 content 含 tool-call，建「回合容器」(思考块+正文气泡+工具调用子列表)；
- 后续 tool/call/tool/result 按 callId 挂进当前回合容器；
- step/start 开 step 分组，回合容器挂在 step 下；
- 同名多工具调用呈现为「本回合调用 N 个工具」，每个条目带参数摘要，一眼区分。
不变量：不动 Agent/ontology 逻辑、不改后端，只改前端会话流渲染；保留折叠卡/JSON 高亮/决策卡/审批卡。

## 五、与原型的关系

原型 his-prototype/index.html 会话流同样是扁平 foldCard；但工作区扫描页用 trc() 解析轨迹(Resolution Trace)聚合呈现处理过程(分类/策略解析/规则装配/一致性前置)，标题即写明「命中 3 · 过滤 1」，是可参考的轨迹聚合形态。
焕新落地时两者统一：会话流按回合分组(精简)，详细轨迹沉淀到工作区/轨迹区(聚合)。
