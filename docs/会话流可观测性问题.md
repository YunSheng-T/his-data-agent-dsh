# 会话流可观测性问题记录（含跨 step 重复调用）

> 修正：本记录有两层问题。第一层（同一步批量调用）是正常行为；第二层（跨 step 重复调用同一工具）是真实存在的模型行为问题，需「轨迹」视图暴露 + 诊断。

## 一、问题现象

本体驱动扫描场景（dbscript/*.sql）会话流里出现大量重复步骤：获取规则(policy_get_rules)多次、获取规则实现(rule_get_implementations)更多、code_lint 等质量工具跨步骤重复调用，个数不稳定。一度怀疑是按钮没防抖（已排除），也一度认为是前端扁平渲染导致的视觉重复（不完整）。

## 二、根因（session log 实证，两层）

### 第一层：同一步内批量调用（正常，非重复）

一个 step = 一次模型决策回合；step 内多个 tool/call = 那一次决策批量要了多个工具结果。
证据：assistant/message 的 content 数组一次含 3 个 tool-call block(policy_get_rules x3)，后续 tool/call 的 callId 连续(call_00/01/02)、参数各不同(3 个不同 policy)。
调用次数由本体数据决定：dbscript 平台被 3 组策略覆盖 -> policy_get_rules x3；4 条规则 -> rule_get_implementations x4。符合「策略与规则必须分层取全」约定。

### 第二层：跨 step 重复调用同一工具（真实存在，需修）

扫描 session log 发现大量「同工具 + 同参数」在不同 step 重复出现，例如：

- session-358a3a9e：step8 code_lint(path, view:working) -> step9 code_lint(path, view:working) 完全重复 -> step10 code_lint(path) 第三次；
- session-3afc3827：model_lint 在 step1/7/8/10 反复调同一模型；
- session-0a3f6749：model_read_fields/model_lint/todo_write 跨 step 重复。

看 step8->step9 的 assistant 消息：step8 说「扫描计划收口… code_lint/danger_scan/check_consistency」批量调 3 个；step9 拿到工具结果后说「danger_scan 通过… code_lint…」又重复调了一次 code_lint。

**结论：真实模型在多轮里，看到前面工具结果后，会重复调用已调用过、结果已返回的工具（同参数）。这不是前端渲染问题，是模型行为。**

可能诱因：1) 模型没意识到工具已调过/结果已回；2) 流式/重试机制产生重复；3) 上下文里历史工具调用被重复呈现，模型又发一次。需进一步定位（见「待办」）。

## 三、可观测性缺口（前端 renderEvents）

1. assistant/message 只提取 text 渲染气泡，忽略 content 里多个 tool-call block，丢失「这一次回复要了哪些工具」语义；
2. 每个 tool/call 独立 foldCard，3 个同名 policy_get_rules 铺成 3 张独立卡；
3. step/start 只加「步骤 N」文字标签，没把「步骤 → 本次回复的多个工具」组织成整体；
4. 跨 step 的重复调用没有显式标注，用户看不出「step8 调过 code_lint，step9 又调了一次」。

## 四、方向：DSH-Desktop 式「轨迹」视图（用户截图为准确形态）

用户提供 DSH-Desktop 截图（会话流「对话/轨迹」标签）。「轨迹」不是按 step 分块的卡片，而是**按时间轴组织的详细执行历程**：

- **时间轴**：顶部刻度（输入/总耗时/Token/模型），按时间顺序铺开每一步；
- **每条记录**：`工具 名称(参数摘要)` → `助手 结果摘要`，逐条带耗时；
- **统计**：底部 `103 轮 · 2133 步 | LLM 363 分 27 秒 · 工具调用 163 分 49 秒 | 每 token 4.1 秒 · 107 tok/s`；左上 `时长 6 分钟 · 轮数 2 · 调用 5`；
- **「对话」标签** = 消息气泡流；**「轨迹」标签** = 上述时间轴；同屏可切；
- 关键价值：重复调用、耗时爆炸、链路长度在时间轴上一眼可见（这是 Observable/Performance 面板式的呈现）。

### 轨迹视图要点（对齐截图）

- 按**时间轴**组织（不是按 step 分块卡片）；每条 = 工具名+参数摘要 -> 结果摘要，带时间戳；
- 顶部/底部有**统计条**（轮数/步数/LLM 时长/工具调用时长/token 速率）；
- 支持「对话 / 轨迹」标签切换；
- 数据来源：session 事件流（turn/start、step/start、tool/call、tool/result、reasoning-chunks、assistant/message 均带 time）。

> 注：早期曾误实现为「按 step 分块 + 重复标注」的卡片视图（beginStepTrace/traceToolLine），经用户反馈已撤销（commit 4b739a4），换成截图所示时间轴式轨迹。

### 源码研究结论（DSH 官方 ui-trajectory）

DSH 上游 deepseek-ai/deepseek-harness（DSH-Desktop 内嵌它的 Web UI）里，「轨迹」是**独立于「对话」的第二个 event-to-view 投影**：

- **包**：`packages/client/ui-trajectory`（对话是 `ui-chat`）。
- **核心投影**：`trajectory-event-projection.ts`，注释 `Chat and Trajectory own independent event-to-view projections`——把 session 事件（turn/start、step/start、tool/call、tool/result、reasoning、assistant/message）投影成 **ledger view（逐条账本）**，每条含角色/工具名/参数摘要/结果摘要。
- **UI 组件**：`TrajectoryTimeline`（时间轴）、`TrajectoryTable`（表格）、`TrajectoryTurnHeader`（轮次分组头）、`TrajectoryCell`（单元格）、`TrajectoryToolbar`（工具栏）、`duration-store`（耗时聚合）、`trajectory-snapshot-builder`（快照）。
- **统计来源**：`duration-store` 按轮次/步骤聚合 LLM 耗时、工具调用耗时；`StatsLine` 展示 轮数·步数 | LLM 时长 · 工具调用时长 | token 速率。
- **数据模型**：`trajectory-contract.ts`（contract/types）、`trajectory-record.ts`、`trajectory-search-index.ts`、`trajectory-virtual-rows.ts`（虚拟滚动）。

> 结论：我实仓 studio-ui 目前只有「对话」流（foldCard/回合分组），缺一个独立的「轨迹」视图。要真正对齐 DSH-Desktop，应新增一个基于 session 事件流的 trajectory 投影（ledger 时间轴），而非改对话流。
