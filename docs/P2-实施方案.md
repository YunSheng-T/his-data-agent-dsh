# P2 实施方案 · 多空间联动 / 子 Agent 并行 / 资产运营闭环

> 依据：技术方案 §13 演进路线 + P1 任务书「明确不做」边界（反向提醒推迟到 P2）。
> 原则延续：Provider seam 可替换、审批三级门禁不变、UI 纯渲染、断言先行。

## 范围分解

### P2-1 多空间联动 · 模型变更 → ETL 反向提醒（本次实施）

P1 已做单向（codegen 读模型 / asset_sync 回写血缘）。P2-1 做反向：模型变了，开发侧受影响作业自动浮出水面。

| 项 | 类型 | 内容 |
|---|---|---|
| `ast.js` parseEtl 解析 `@model` 注解 | 改动 | 新增 `modelFile` / `modelVersion` 字段（codegen 生成的文件头已带该注解，P1 已埋点） |
| `lineage.js` `jobsForModel(repo, modelFile)` | 新建 | 模型 → 引用它的作业清单（@model 注解优先，targetTable 尾名兜底），含各作业代码基线版本 |
| dev 工具 `impact_check`（read 级） | 新建 | 入参模型文件，返回 `{jobs:[{path, baseVersion, currentVersion, stale}]}`；供 Agent 在模型变更后主动排查 |
| `workspace-anchor`  repo 锚定提醒 | 改动 | 锚定到分支/目录时，对目录内 .etl 做 staleness 检查，注入 notice 追加「⚠ 模型已更新，以下作业代码基于旧版本生成」 |
| studio-ui `/api/repo/tree` | 改动 | 每条 etl 加 `stale` 标记；前端树徽标「模型已更新」 |
| `assert-impact.mjs` | 新建 | 注解解析 / 反查 / 版本升级后 stale 命中 / 锚定提醒注入 / 树标记 |

设计要点：
- staleness 是**实时计算**（jobIndex 扫已提交视图 vs 模型服务当前版本），不维护第二份状态，不落事件表；
- 提醒语义 = 「代码注释里的标准引用可能过期」，修复路径是既有工具链（etl_codegen 重新生成 → lint → dryrun → commit → publish），不新增写工具；
- 未提交工作区改动不参与 stale 判定（以已提交视图为准，与血缘同一语义）。

### P2-2 子 Agent 并行（下一步，需先穿刺 M2）

P0 为防自主委派失控，显式摘除了整套 subagent。P2-2 要回答：
- dsh Developer Preview 的 subagent 生命周期（隔离 context？共享审批管线？tool/code-dispatch 事件形态？）——**M2 穿刺先行**；
- 审批策略必须穿透子 Agent（子 Agent 内 gated 工具走同一个 approval/request）；
- 候选场景：多作业批量 lint/dryrun 并行、影响面批量重生成。
- 风险：若子 Agent 绕过审批或事件不落主 Session Log，P2-2 降级为「编排内并行 Promise」（run_code 程序内并发，无子 Agent）。

### P2-3 资产运营闭环（最后）

- 资产目录 mock Provider 已有 assets/lineage 两张表；P2-3 加运营视图（资产清单 + 血缘计数 + 质量门状态聚合端点 `/api/assets`）+ UI 资产目录页（左栏菜单第三项点亮）；
- 不做真实下线流（原型外）。

## 验收（P2-1 部分）

1. 模型 commit 升版后，`impact_check` 立即报出基于旧版本生成的作业；
2. 锚定到受影响目录时，注入 notice 带过期提醒并落 Session Log；
3. studio 目录树 stale 徽标与 `impact_check` 结果一致；
4. P0/P1 全部回归保持绿色。
