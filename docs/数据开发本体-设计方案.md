# 数据开发本体 · 设计方案（V2 · 基于 Palantir Ontology 五原语）

> 定位：在了解 Palantir Ontology 之后重新设计。本体 = 语义层 + 动力学层的「操作层」，不是规则库。
> 前提：数据开发本体建立在「通用本体平台」之上（平台提供五原语的建模/运行时/治理），本方案只定义「数据开发领域」这一层。

## 0. 一句话

数据开发本体 = 把「模型/作业/平台/字段/标准/版本」建模为 Object + Link（语义层），把「生成/提交/发布/扫描/血缘」建模为 Action + Function（动力学层），Agent 通过它理解上下文并受控执行。

## 1. 语义层 · Object Types（业务世界里有哪些东西）

| 空间 | 对象类型 | 说明 |
|---|---|---|
| 建模空间 | Model（模型） | 物理表名、名称、域、分层、当前版本、发布态 |
| | Field（字段） | 名、类型、中文说明、标准绑定 |
| | DataStandard（数据标准） | code、版本、规则、状态 |
| | ModelVersion（模型版本） | 版本号、变更摘要、发布号 |
| 开发空间 | PlatformInstance（平台实例） | 名、形态(低代码/高代码)、引擎 |
| | JobType（作业类型） | 所属平台实例、名 |
| | Job（作业） | 路径、引擎、目标物理表、代码 |
| | Directory（作业目录） | 路径 |
| | Repo / Tenant（仓 / 租户） | 多租户 |
| 治理空间 | Policy（治理目标） | 名、目标、覆盖的平台（covers） |
| | Rule（规则） | 名、严重度、阶段、所属 Policy、挂平台 |
| | RuleImpl（规则实现） | 引擎、规则集版本、绑作业类型 |
| 引用层 | Release（发布） | 发布号、commit、含模型版本 |
| | ModelIncrement / CodeIncrement | 双侧增量事实 |
| 实例层 | ScanRun / Finding | 运行产物（回挂本体） |

## 2. 语义层 · Link Types（有向、有类型、可带属性）

| 关系 | 方向 | 说明 |
|---|---|---|
| implements | Job → Model | 物理表名匹配推导（零绑定） |
| hasField | Model → Field | 字段归属 |
| binds | Field → DataStandard | 标准绑定 |
| hasVersion | Model → ModelVersion | 版本链 |
| hasIncrement | ModelVersion → ModelIncrement | 设计侧增量 |
| instanceOf | Job → JobType | 作业分类 |
| hasJobType | PlatformInstance → JobType | 实例有作业类型 |
| inDirectory | Job → Directory | 作业树 |
| releaseBaseline | Release → Job | 最近发布即基线（零存储） |
| containsRule | Policy → Rule | 策略聚合规则 |
| covers | Policy → PlatformInstance | 治理目标跨平台覆盖 |
| appliesTo | Rule → PlatformInstance | 规则挂平台 |
| implementedBy | Rule → RuleImpl | 规则多实现 |
| bindsJobType | RuleImpl → JobType | 实现挂作业类型 |

## 3. 动力学层 · Action Types（可以对对象做什么，受治理）

每个 Action = Parameters（参数 Schema）+ Submission Criteria（前置校验）+ Side Effects（副作用）+ 权限（gated 审批）。

| 对象 | Action | 提交条件 / 副作用示例 |
|---|---|---|
| Model | model_create / model_alter_field / model_bind_std / model_commit / asset_register | 提交前：分层合法、标准存在；副作用：版本+1、发布态 |
| Job | etl_codegen / dag_gen / etl_patch / repo_commit / sched_publish / asset_sync | 提交前：lint 无 error、dry-run 过；副作用：触发 CICD、血缘回写 |
| Ops | ops_gen / ops_deploy | 提交前：配对/环检测；副作用：制品包、回调 |
| 治理 | propose | 副作用：进本体平台治理审批 |

→ 这些就是现有 domain-tools-* 的 gated 写工具，需把「提交条件/副作用/权限」显式化为 Action 契约（现有 approval-policy + 工具层自检已是雏形）。

## 4. 动力学层 · Functions（怎么计算，注册到本体、可被发现）

| Function | 输入 → 输出 | 说明 |
|---|---|---|
| classify | Job(+特征) → JobType | 语义分类推理 |
| consistency_check | Job × ModelVersion区间 → 四态 | 编排入口：本体取规则 → 扫描引擎执行 → Finding 回挂本体 |
| lineage_upstream / downstream | Job → 血缘 | 图遍历 |
| impact_check | Model → 受影响作业 | 反向联动 |
| explain | Finding → 归因链 | 沿关系回溯 |

→ 这些就是现有 scan/lint/lineage 只读工具，需注册到本体（关联"操作的是哪种实体"）。

## 5. Interfaces（多态，统一操作）

「可发布对象」（模型/作业都实现 publish）、「可版本化」、「可绑定标准」——让 Agent 用一套逻辑处理多类对象（面向接口编程）。

## 6. 扫描规则（Policy/Rule/RuleImpl）的正确位置 · 路线 B

**Policy / Rule / RuleImpl 是 Object Type（本体实体），但不是独立的原语**（五原语里没有「规则」这一种）。它们作为**普通对象**建模：

- Policy（治理目标）、Rule（规则）、RuleImpl（规则实现）都是 Object Type，与 Model/Job 平级；
- 通过 Link 关联：Policy →containsRule→ Rule →implementedBy→ RuleImpl；Rule →appliesTo→ PlatformInstance；Policy →covers→ PlatformInstance（跨平台）；
- 被 **Function** 引用：consistency_check 读取这些 Rule 对象做校验，explain 沿 containsRule/appliesTo 回溯归因；
- 被 **Action** 引用：Action 的 Submission Criteria 可引用 Rule（提交前校验）。

**地位变化**：从「独立原语/治理引擎核心」降为「普通 Object Type」——不再有特殊地位，但**保留实体**，可版本、可审计、可跨规则复用。

这纠正了上一版（含《本体模型重构方案》）把 Policy/Rule/RuleImpl 当「本体核心/独立原语」的偏差——它们是本体里的对象之一，不是本体的全部。

## 7. 与现有实现的关系

- domain-tools-modeling/dev/ops 的 30+ 工具 = Action + Function 的雏形（已在对象上操作），但缺：Object/Link 显式建模、Action 的提交条件/副作用显式化、本体可发现性
- ontology_classify/policies/rules/match_increment/explain/propose 6 工具 = 把「规则」当成了独立原语而非普通对象；应把 Policy/Rule/RuleImpl 建模为 Object Type + Link，工具归位为 Function（consistency_check 引用规则对象、explain 沿规则关系归因）
- PACKAGE_REGISTRY / manifest = PlatformInstance 的一部分（平台实例映射）

## 8. 重构路径（分层建设）

① Object + Link 显式建模（含 Policy/Rule/RuleImpl 作为普通对象 + 治理关系）→ ② 工具归位 Action/Function + 补治理声明 → ③ consistency_check 等 Function 引用规则对象做校验 → ④ 本体可发现（MCP/SDK 元数据），Agent 先定位实体类型再选 Action/Function

## 9. 扫描能力的归属（三层分工）

**扫描的「执行」不是本体的范畴，是扫描引擎/CICD 的范畴。** 三层分工：

| 层 | 职责 | 例子 |
|---|---|---|
| 本体（定义层） | 声明对象/关系 + Rule（语义/严重度，**不含执行代码**）+ RuleImpl.engine 指向执行器 | Rule「字段类型一致性」声明；engine=se-sql 1.8 |
| 扫描引擎/CICD（执行层） | 实际执行校验：SQL 解析、lint、危险检测、一致性比对，产出 Finding | se-sql 1.8 解析器跑真实校验 |
| Agent/Function（编排层） | 本体取规则 → 引擎执行 → Finding 回挂本体 + 归因 | consistency_check / explain |

**关键**：Rule 只声明「扫什么、为什么」，RuleImpl.engine 是「本体 → 扫描引擎」的绑定契约；「怎么扫」永远在扫描引擎。门禁只认流水线（扫描引擎）的权威结果。本体因此不会变成「另一个扫描引擎」。
